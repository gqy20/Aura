# GLM vs MiniMax 提取基准报告

> 基准日期：2026-10-18。脚本：`scripts/llm_quality_bench.py`（60 次调用：4 配置 × 15 次）。
> 任务：同一张牛肉面照片 → forced tool call（vision + `submit_meal_record` schema，生产提取路径）。
> 原始数据：`app/build/llm-bench-results.jsonl`。

## 汇总

| 指标 | GLM 5.3-flash<br>thinking off | GLM 5.3-flash<br>thinking on | MiniMax-M3<br>thinking off | MiniMax-M3<br>thinking on |
|------|:---:|:---:|:---:|:---:|
| 成功率 | 15/15 | 15/15 | 15/15 | 14/15 |
| 耗时中位数 | **8.0s** | 23.8s | **7.3s** | 8.8s |
| 耗时均值 | 8.9s | 26.3s | 7.3s | 9.3s |
| 耗时最大 | 14.3s | 35.3s | 10.3s | 13.7s |
| input tokens | ~1496 | ~1496 | ~1* | ~1* |
| output tokens | **~153** | ~989 | ~446 | ~696 |
| kcal 中位数 | 810 | 910 | 1115 | 1000 |
| kcal 标准差 | **±100** | ±92 | ±175 | ±119 |
| kcal 范围 | 600-970 | 777-1065 | 820-1345 | 760-1260 |
| 条目数分布 | **全部 2** | 2-6 波动 | 2-7 波动 | **全部 2** |
| 中文菜名 | 15/15 | 15/15 | 15/15 | 14/14 |
| 数值合理 | 15/15 | 15/15 | 15/15 | 14/14 |

*MiniMax API 的 input_tokens 恒报 1（协议层 bug），实际计费含图片 token（估计与 GLM 量级相近 ~1500）。

## 关键发现

### 1. Thinking 模式不值得开

**这不是推理任务**——"看图 + 填 schema"是感知型任务，thinking 的价值在多步推理，不在视觉识别。数据完全支持：

- **GLM thinking on**：速度慢 3 倍（8s → 24s），输出 token 多 6.5 倍（153 → 989），但方差几乎没改善（±100 → ±92）；更糟的是**条目数从稳定 2 项变成 2-6 波动**——thinking 让模型"过度思考"，把葱花、酸萝卜丁都单独算一项，破坏了输出一致性
- **MiniMax thinking on**：速度几乎不变（MiniMax 的异步推理架构），方差有改善（±175 → ±119），条目数从波动变稳定 2——但**有 1 次失败**（15 次里 1 次未返回 tool_use），且输出 token 仍多 55%

### 2. 质量排名

照片内容是**牛肉面 + 炸物**（真实热量约 750-1080 kcal）：

- **GLM off（810 kcal，±100，全部 2 项）**：最接近真实值、方差最小、条目数完全稳定——**综合最优**
- MiniMax on（1000 kcal，±119，全部 2 项）：合理但整体偏高 ~15%
- GLM on（910 kcal）：数值合理但条目数不稳
- MiniMax off（1115 kcal，±175）：系统性偏高 + 方差最大 + 条目数波动 2-7

### 3. 成本估算

以每次提取为单元（flash 级定价，百万 token 计价）：

| 配置 | 每次总 token（估） | 相对成本 | 每千次成本估算 |
|------|:---:|:---:|:---:|
| GLM off | ~1650 | **1.0x（基准）** | ≈ 0.5-1 元 |
| GLM on | ~2560 | 1.55x | ≈ 0.8-1.6 元 |
| MiniMax off | ~1950（估） | ~1.2x | ≈ 0.6-1.2 元 |
| MiniMax on | ~2240（估） | ~1.36x | ≈ 0.7-1.4 元 |

GLM off 输出 token 极少（~153）是因为 schema 填充本身就是短输出——这正好是 flash 级模型的甜点区。

### 4. 输出风格差异

- **GLM** 偏保守：菜名倾向"牛肉粉（汤粉）"级别的**聚合名**（跟密度表核心名匹配更友好）
- **MiniMax** 偏具体：菜名倾向"炸春卷"、"胡萝卜丁"级别的**具体物**（单次信息量大，但跨次一致性低）
- 这个差异影响密度表命中率：GLM 的聚合名更容易命中"牛肉粉"核心名，MiniMax 的"红烧牛肉面（宽面）"需要子串匹配

## 结论与建议

| 维度 | 推荐 |
|------|------|
| **默认生产配置** | **GLM glm-5.3-flash + thinking off**——最稳定（±100、2 项）、够快（8s）、最便宜（~153 output tokens）、聚合名利好密度表 |
| **速度优先** | MiniMax off（7.3s vs 8.0s 差距很小，不值得为这 0.7 秒牺牲方差） |
| **thinking 模式** | **一律关闭**。感知型任务不需要推理；开启只会拖慢 + 增加 token + 破坏条目稳定性（GLM）或偶发失败（MiniMax） |
| **MiniMax 定位** | 备用 Provider。方差偏大（±175 vs ±100）且 kcal 系统性偏高 ~15%，但绝对值仍在合理区间 |

## 已知协议 bug

MiniMax `/anthropic/v1/messages` 的 `usage.input_tokens` 恒返回 1（60 次调用全部如此），不影响功能但**用量监控和成本核算不可信**——如有计费争议以此为准向 MiniMax 反馈。

## 补充：MiniMax-M3.1-Flash-Preview（2026-10-19 追加）

用户要求补测 M3.1。模型列表（`/v1/models`）确认实际名称为 `MiniMax-M3.1-Flash-Preview`（普通 `MiniMax-M3.1` 名会被宽松路由到 M3）。

### 协议差异（关键）

**M3.1 强制 thinking，不可禁用**：发送 `thinking: {"type": "disabled"}` 直接 400——
`"requires adaptive thinking; thinking.type=\"disabled\" (including reasoning.effo..."`。
"Flash" 变体不是"更快"，而是"轻量推理不可关"。这从协议层堵死了提取场景的"关思考提速"路径。

### 基准数据（15 次，仅此一种模式）

| 指标 | M3.1-Flash-Preview | 对照：M3 off | 对照：M3 on | 对照：GLM off |
|------|:---:|:---:|:---:|:---:|
| 成功率 | **11/15（73%）** | 15/15 | 14/15 | 15/15 |
| 耗时中位 | 16.1s | 7.3s | 8.8s | 8.0s |
| kcal 中位 | 1114 | 1115 | 1000 | 810 |
| kcal 标准差 | **±194** | ±175 | ±119 | ±100 |
| 条目数 | 4-9 | 2-7 | 全 2 | 全 2 |
| output tokens | ~970 | ~446 | ~696 | ~153 |

### 结论

**M3.1-Flash-Preview 不适合本场景**，理由按严重性排序：

1. **27% 失败率**（15 次里 4 次 400/异常）——提取是高频操作，这个成功率不可接受
2. **强制 thinking**——无法走"关思考提速"路径，从协议层堵死了 30 秒闭环的优化方向
3. **方差最大**（±194 vs GLM off 的 ±100）——自动 thinking 反而让"过度思考"更严重
4. **条目粒度过细**（4-9 项）——把"红油汤底"、"葱花"都单独算一项，破坏一致性
5. **最慢的 MiniMax 选项**（16.1s vs M3 off 的 7.3s）

名字里的 "Flash-Preview" 有误导性——它不是"更快"，而是"推理不可关的轻量模式"，且是 Preview 状态。

**维持原有结论**：GLM glm-5.3-flash + thinking off 为默认生产配置。MiniMax M3（非 M3.1）继续作为备用 Provider。
